You are the Replit Agent working on **AccessiBooks**, an accessibility-first audiobook and reading platform for people with disabilities in Australia.

Your job is to **analyze the existing codebase and implement the following feature set as clearly defined parallel tasks**, grouped by architecture layer. Break work into independent modules where possible, minimize coupling, and create a delivery plan that allows multiple tasks to be built concurrently.

## Product Context

AccessiBooks is designed as an inclusive digital reading and listening platform with web, mobile, and desktop ambitions. It must center accessibility, user independence, cognitive support, and compliance with Australian disability expectations and digital accessibility standards.

The product should align with:

* WCAG 2.2 AA accessibility principles
* Australian Disability Discrimination Act 1992 (DDA)
* Australian Privacy Principles (APPs)
* Accessibility-first design for people with physical disabilities, sensory disabilities, neurodivergence, dyslexia, cognitive disability, and people who use assistive technologies

The system should also support future positioning as:

* a low-cost assistive technology offering
* a capacity-building tool
* an NDIS-friendly digital product

## Primary Goal

Implement a cohesive accessibility and monetisation upgrade for AccessiBooks, including:

1. Accessibility Profiles
2. Voice Navigation
3. Cognitive Simplification
4. Accessibility-Aware Search
5. Sensory Regulation Mode
6. Interactive Transcript Enhancements
7. Community Accessibility Annotations
8. Offline and Low-Bandwidth Mode
9. NDIS-Friendly Usage Reporting
10. Business-model-ready subscription and institutional support scaffolding

## Execution Instructions

1. First inspect the existing codebase and identify:

   * current frontend framework
   * backend stack
   * database structure
   * auth flow
   * audio/transcript architecture
   * search implementation
   * deployment setup

2. Then break implementation into **parallel workstreams** with:

   * task name
   * purpose
   * files/services affected
   * dependencies
   * API contracts
   * acceptance criteria

3. Prefer modular architecture. Avoid giant rewrites unless necessary.

4. Where the codebase is incomplete, scaffold cleanly with TODO markers and stable interfaces.

5. Preserve backward compatibility where possible.

6. Make every UI component keyboard accessible, screen-reader friendly, and compliant with WCAG 2.2 AA.

7. Use plain language in user-facing copy.

8. Where relevant, add analytics hooks for feature usage, but ensure privacy-sensitive data handling.

9. Create a final implementation summary and identify which tasks can be completed independently in parallel.

# Required Parallel Workstreams

## Workstream A: Accessibility Profile System

Build a persistent accessibility profile system.

### Requirements

* Create or extend user profile schema with fields:

  * playbackSpeed: float
  * fontType: enum(default, dyslexia_friendly)
  * contrastMode: enum(normal, high, dark, sepia)
  * cognitiveMode: boolean
  * motionReduction: boolean
  * sensoryMode: boolean
  * transcriptPreference: boolean
  * voiceNavigationEnabled: boolean
  * lowBandwidthMode: boolean
* Store these preferences in the backend database
* Sync preferences across sessions and devices
* Apply preferences globally on login
* Create an “Accessibility Settings” panel with real-time preview
* Include “Reset to Safe Defaults” action
* Ensure settings are persisted and cached safely

### Deliverables

* schema changes
* backend CRUD endpoints
* frontend settings UI
* global preference application layer
* tests

### Acceptance Criteria

* a logged-in user can save and retrieve accessibility settings
* settings are applied automatically when the app loads
* all settings can be reset to defaults
* controls are keyboard accessible and screen-reader labeled

---

## Workstream B: Voice Navigation and Voice Interaction

Implement voice-controlled navigation and interaction.

### Requirements

* Add voice input capability using an appropriate speech-to-text approach
* Support commands such as:

  * Play next chapter
  * Pause
  * Slow down
  * Speed up
  * Open transcript
  * Explain this
  * Find easier books
  * Enable low sensory mode
* Build a lightweight intent parsing layer for known commands
* Provide both visual and audio confirmation feedback
* Include graceful fallback to manual controls
* Add permissions handling and privacy-safe messaging

### Deliverables

* voice input service
* command parser
* UI controls for enabling/disabling voice mode
* integration with player, transcript view, search, and settings
* accessibility-compliant feedback system

### Acceptance Criteria

* supported commands execute reliably
* users can disable voice mode easily
* no voice control path is required for core access
* system works without blocking manual interaction

## Workstream C: Cognitive Simplification Engine

Create a cognitive accessibility mode for transcript and content support.

### Requirements

* Add a “Simplify Content” toggle
* When enabled:

  * break transcripts into smaller chunks
  * generate simplified summaries for sections
  * highlight key ideas
  * expose an “Explain this section” action
* Design this as a pluggable service so AI summarisation can be swapped or upgraded later
* Target plain-language summaries around an easy-reading level
* Cache generated summaries for performance
* Add clear disclosure when content is AI-simplified

### Deliverables

* simplification service interface
* content chunking logic
* summary storage/caching layer
* transcript UI enhancements
* explain-this interaction

### Acceptance Criteria

* simplified mode can be enabled or disabled per user preference
* transcript sections display chunked and simplified content when requested
* the system fails gracefully if summarisation is unavailable
* user can still access original transcript at all times

## Workstream D: Accessibility-Aware Search and Metadata

Enhance search to support accessibility-driven discovery.

### Requirements

* Extend content metadata schema with:

  * readingLevel
  * narrationType
  * transcriptAvailable
  * sensoryLevel
  * chapterLength
  * accessibilityTags
  * languageComplexity
* Add filters for:

  * easy / standard / advanced reading level
  * human / AI narration
  * transcript available
  * low sensory content
  * short / medium / long chapters
* Update search indexing and query logic
* Build accessible filter UI
* Support combined filter selection
* Ensure empty states and result explanations are understandable

### Deliverables

* metadata schema extension
* indexing updates
* search API changes
* frontend filter panel
* result cards showing accessibility metadata

### Acceptance Criteria

* users can search and filter content based on accessibility needs
* metadata appears on content detail pages and results
* search remains performant and usable with multiple filters

## Workstream E: Sensory Regulation Mode

Implement a low-stimulation experience mode.

### Requirements

* Add a “Low Sensory Mode” toggle
* Reduce or disable non-essential animations and transitions
* Simplify visual layout where appropriate
* Normalize audio playback volume to reduce spikes
* Optionally support a calming sound layer scaffold, but keep it disabled by default unless already supported
* Integrate with saved accessibility profile
* Ensure compatibility with reduced motion OS settings

### Deliverables

* motion reduction layer
* low-sensory UI mode
* audio normalization logic or service hook
* integration with settings/profile system

### Acceptance Criteria

* enabling sensory mode visibly reduces stimulation
* app remains fully functional in this mode
* OS/system reduced motion preferences are respected

### Acceptance Criteria

* keyboard and assistive technology users can navigate transcript effectively

### Acceptance Criteria
